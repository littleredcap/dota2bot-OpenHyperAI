## 1. 文档用途与需求来源

这份文档持续记录我们要解决的问题、验收方式、当前状态和未定项。新增需求先更新这里，再关联实现 PR；不把研究候选、架构建议或尚未执行的测试写成已完成成果。

来源分为：

- **U：用户明确要求。** 本轮及可见前序消息中直接提出的目标。
- **D：设计决定 / 工程推导。** 为满足 U 类目标采用的技术约束，允许在有证据时调整，不声称是用户逐条指定。
- **O：待定。** 影响环境或验收的选择，目前没有已确认答案。

项目的工作方向已进一步由用户确认：**选择 A——在公平条件下尽可能提高实战获胜概率，不以拟人化为约束，不通过额外金币、经验、属性或非法信息提高难度。** 现有 OpenHyperAI 的正确性和版本兼容是基础；对线、团战、地图运营及阵容适应是待逐项验证的获胜路径。是否“更强”必须由相应数据支撑，不以代码量、单项经济指标、其他 Fork 的宣传或单个离线用例代替结论。

### 3.1 TP 往返：风险来源与尚未证实的边界

目前**不能声称我们的 OHA-Next 已被证实存在 TP 往返 Bug**。证据如下：

1. **E1 外部报告：** [canshuqwp 的 c06f5df8 提交](https://github.com/canshuqwp/dota2bot-OpenHyperAI/commit/c06f5df8bbf2da88f0bfabee1ee945cf51c05027) 的作者称：换位或临时换线后，Bot 对线期 TP 到职责默认线路，却又被对线行为拉回实际线路。该 Fork 在自己的代码中禁用了对线期该 TP 分支。我们没有其原始对局日志。
2. **E2 当前源码静态依据：** [ability_item_usage_generic.lua 的 GetLaningTPLocation](../bots/ability_item_usage_generic.lua) 用 `J.GetPosition(bot)` 和阵营固定表推导 TP 线路；同文件对线模式下调用这一结果。[mode_laning_generic.lua](../bots/mode_laning_generic.lua) 则可能按 `GetAssignedLane()` 或自定义 lane 选择目标。如果两套来源不一致且 TP 条件成立，就**可能**触发相互冲突的移动目标。
3. **未核实：** 实际位置交换后这些线路是否必然不同、模式竞争与 TP 施法能否形成往返、多久出现一次、7.42 环境是否仍可触发。其他 Fork 的修复提交不等于我们当前源码已经重现。
4. **调查验收：** 先定义自定义换位/临时换线测试输入，检查两种线路是否可能不一致；再在 Lua 隔离测试中证明条件；若需要正式认定“游戏中 TP 往返”，还须该版本实机证据。若发现状态一致或无法复现，则将此候选保持观察或关闭，而不是为了满足表格而强行改代码。

**P0 只有 F-01 的“核对目标版本”作为当前审查优先项**；F-02 和 F-03 不是已确认的 P0 Bug，改为有证据后才决定是否修复。原先把这三类都写成“P0 问题”是不准确的。

### 3.2 功能需求的推荐推进节奏

- **第一批：优先做 F-01 目标版本差异核对，并调查有明确来源的风险。** F-02/F-03 只有在指向具体技能、模式及触发输入且具备 E2/E3 证据后，才单独提出修复 PR；不预设它们一定有 Bug。复用已有 Lua 回归 CI。
- **第二批：对线与团战。** 优先 F-04 / F-05 的单个问题，参考其他 Fork 的具体提交但不整库导入。
- **第三批：团队运营与目标。** 逐项实施 F-06 / F-07，再考虑 F-08 / F-09。
- **暂不安排：** 独立引擎观察者、watchdog、批量实战平台、自动数据回传。这些需求保留，但从实施依赖中移出。

每个功能 PR 要写清楚：问题场景、当前行为、期望行为、涉及英雄/模式、边界输入、测试用例、已知未实机验证项、回退方式。必要的运行数据或日志可在将来补充；不为了“先上监控”而中断功能改进。

### 3.3 F 类需求的获胜导向验收补充

| 功能组 | 除局部逻辑正确外，还要回答什么 | 不能仅据什么判定“更强” |
| --- | --- | --- |
| F-01（版本兼容） | 是否避免英雄/物品/目标错误，让既有合法操作在 7.42 正常工作 | 兼容文件数量或 Lua 语法通过 |
| F-02/F-05（团战与技能） | 是否减少高代价错误交战、关键技能浪费、错误目标和错过击杀/救援机会 | 技能释放次数、命中率或击杀数 |
| F-03（行为稳定） | 是否减少有证据的无效决策消耗，且不破坏原本合理的等待/埋伏 | 移动次数、动作数量 |
| F-04（对线经济） | 是否把资源优势有效兑换成可控风险的团战、地图目标与胜利 | 补刀、GPM/XPM 单项 |
| F-06/F-07（团队运营与地图目标） | 是否在推进、防守、Roshan/Tormentor、劣势资源交换中做更有利于最终胜率的选择 | 参与人数、打盾次数、单次推塔 |
| F-08/F-09（适应与覆盖） | 是否在更多对手、英雄、阵容和局势下维持胜率、不出现关键退步 | 单一强势英雄或固定敌方组合的战绩 |

在缺少真实公平对照前，上述“更有利于胜利”只是**研发假设**；可以实现局部逻辑并标注 `logic_checked`，但不得标注 `strength_supported`。证据等级 E0～E4 仅描述**缺陷证据**，不能用来代替强度证据。

### 状态语义

状态使用 `planned`、`in_progress`、`in_pr`、`verified`、`merged`、`blocked`、`deferred`、`reverted`，并注明对象和证据。文档提交完成只证明设计已记录；测试通过不代表代码已经合并；代码合并不自动意味着游戏效果已验证。

## 5. 分层验收与人工投入

| 变更 | 必要证据 | 用户是否需要进入游戏 |
| --- | --- | --- |
| 文档、注释、独立工具 | 与影响相称的格式、链接或工具验证 | 不需要 |
| 局部纯算法 / 明确 Bug | T0 + 对应 T1；涉及引擎交互时补 T2 | 不设为常规要求 |
| 技能、动作中断、团队决策 | T0 / T1 + 针对性的真实自动场景或对局 | 由已配置主机运行；异常才抽查 |
| 正式发布 / 大版本适配 | 相关离线与真实覆盖、数据报告、短时体验抽查 | 可能需要一次短复核，也可由维护者执行 |

尚无真实主机时，行为效果保持“未游戏验证”。可以推进离线基础与文档；不能把测试压力转成要求用户每次手动完成比赛，也不能直接跳过必要的引擎验证。

**2026-11-19 进度变更：** 当前不搭建新的 T2/T3 基础设施。玩法功能 PR 可以先完成代码与 T0/T1 检查，未实机确认的风险保持未验证状态；不以实施故障监控或批量平台作为现在开始改玩法的条件。

## 6. 首场数据闭环验收（延期）

第一次真实试跑的目标是证明系统与证据有效，不是证明机器人更强。以下各项均需实际证据：

1. 固定游戏构建、源码 / 构建身份、配置和可复现的运行清单。
2. 所有预期自定义 bot 发出匹配的启动标记；只 checkout 成功不算脚本已加载。
3. 原始日志可保存并归属到唯一对局，**所有预期 Bot 均有独立位置/行为心跳和覆盖率**；即使在玩家视野之外也能定位自身 Bot。至少一个异常或预定行为场景有可关联的记录。
4. 至少 1 局真实 completed 对局，取得可信胜负和时长，且符合所选评估配置的必需数据有效；超时、崩溃或不确定包另验异常路径，不能替代这项成功闭环验收。
5. 包中包含 `manifest.json`、`events.jsonl`、`result.json`、`validation.json`、`summary.json`、`report.md`、原始日志和校验和。
6. 缺失与不支持字段明确为 unknown / null；公开指标的来源、有效样本和覆盖率。
7. 包经过上传后，助手实际读取指定 run / artifact；若走备用方案，则读取用户附上的压缩包。
8. 使用可控的故障注入验证：Bot 回调继续运行却不行动、发出无效移动命令、Bot Lua 报错/停止回调但引擎实体仍存在、合法守点、死亡与断心跳。对脚本无法继续上报的情况，优先用经过实机验证的独立引擎观测提供坐标；否则只给最后已知坐标、明确监测盲区，不把“无日志”解释为“无 Bug”。
9. 不要求用户手动操作英雄打完整局，也不要求肉眼巡查战争迷雾。首次环境配置或核对脚本加载可能需要短时配合，完成后复用该环境。

先跑通单局，再验收批次报告和失败恢复；无需一开始就提供几十局数据。

## 7. 当前不纳入交付承诺

- 固定的胜率提升百分比、所有英雄都更强、覆盖所有游戏模式。
- 固定日期、固定云费用、已校准的每局耗时或并行数量。
- 用户已经选择 Turbo、只优化某几个英雄或已经具备 Linux 测试机。
- 普通 GitHub 托管 Runner 已经可以直接运行完整 Dota 对局。
- 无人值守系统、自动定时评估、自动分析通知或自动合并已经开通。
- 通过联网大模型实时控制机器人，或把强化学习作为当前依赖。

这些可以在后续成为新需求，但必须明确来源、资源条件和验收。
