## 1. 核心设计：从选人到拆基地，不是逐技能堆功能

每次对局由三个维度共同确定行为：

- **时间和局势**：选人/分路准备 → 对线 → 前中期节奏 → 中后期目标与团战 → 上高/守高/结束游戏；这不是只按固定分钟划分，双方塔、兵线、装备、地图目标和胜负威胁会改变当前任务。
- **角色和英雄**：pos 1～5 与英雄特有机制决定技能、出装、发育与进场方式。相同英雄在不同位置或阵容中的最优行动未必一致。
- **全队与敌我阵容**：优势/劣势、先手/反手、控制/伤害、位移/视野、单抓/团战、分推/正面推进、能否迅速结束比赛，影响每个人的任务。

**默认复用通用策略，只在英雄技能或阵容确实需要时使用专属策略。** 通用决策可以是“这波应该避战/推进”，专属决策是“这名 Meepo / 辅助 / 核心如何执行”。避免每个英雄复制一套团队指挥规则，也不能用统一模板覆盖 Meepo、召唤系或幻象英雄的关键能力。

所有策略都是可选择的**候选行动**，不是事件触发后无条件执行。可用信息 → 合法性 → 收益 → 机会成本 → 风险 → 替代行动 → 成本更高时放弃或撤退。只能使用 Bot 正常局内合法获得的视野/状态；赛后录像的全图信息只供研究。

## 3. 成熟优先：学习可靠打法，再研究不确定的新机制

“成熟”不是代码已经写过或攻略作者说“最强”。各维度独立记录，避免混成一个模糊评分：

| 维度 | 可选状态 | 用途 |
| --- | --- | --- |
| **攻略成熟度 R** | R0 未研究；R1 有机制/社区思路；R2 多个可靠来源支持，并能说清适用条件、反例与替代打法；R3 新版本职业/高分复盘或较可靠比赛统计进一步支持 | 决定该策略**是否足够值得尝试实现**；补丁一变需要降级再核查 |
| **代码覆盖 I** | I0 尚未审查；I1 旧代码或策略原型；I2 静态/离线场景检查；I3 在相应 Dota 客户端验证动作链 | 决定**该功能是否能用**；不能因为社区成熟就把 I0 说成 I3 |
| **强度收益 W** | W0 未公平比较；W1 有初步对照信号；W2 对手/阵容覆盖与不确定性足以支持限定范围的改进 | 决定**能否声称 Bot 变强**；局部用例通过不等于 W1 |
| **版本适用性** | current / needs_patch_review / outdated | 防止把 7.41 技能、地图、物品攻略直接用于 7.42 |

实施规则：

1. **优先候选：** R2/R3 且 API/局内信息能合法获得、收益/机会成本可表述的常用打法。先读现有 OHA 源码：已有正确实现就**不重复写**。
2. **可研究/小范围实验：** R1 新补丁机制或者高潜力少见打法，可以保留原型与 Mock，必要时用默认关闭开关；不抢占已证据充分的通用策略开发。
3. **暂缓：** 机制/内部技能名/施法链不清楚，反例未解释，或使用成本较高、收益无法估计。先写 IDEA 与 VT；不自动发布为强度增强。
4. **及时升级：** 有新的高分复盘、当前补丁攻略、客户端证据或对照数据时再复核。R 不代表“我觉得好用”，需要可追溯来源与版本。
5. **不机械照抄：** 同一攻略中的固定技能顺序、装备时点、英雄克制关系都要按局势、位置、可见信息和队友计划调整。

## 4. 出装必须与 AI 实际可用策略相匹配

**明确研发原则：** 如果某个装备主要价值是新主动技能，而我们目前既没有可靠的 API 支持，也没有能够合理利用它的已验证策略，那么**不应把它放进默认早期/核心购买链**。留待能力具备后按机会成本、英雄职责和实时局势重新评估。

这不是“所有未知新装备永远不买”。装备仍可能具有确定的被动属性、明显的反制价值或无需复杂操作的收益，必须逐项核验；购买结果还取决于当前经济与角色，不能仅因为玩家攻略建议“必出”就无条件下单。

### Meepo 7.42 魔晶具体案例

- Valve 7.42 把 Shard 从旧 Dig（现由 Scepter 提供）更改为 **Divided We Stand 拾取/Fling 主动**；当前 [PR #5](https://github.com/littleredcap/dota2bot-OpenHyperAI/pull/5) 只是默认关闭的实验决策。
- 在实际可靠释放和机会成本未验证前，**默认 pos1/pos2/pos3～5 出装不再于散失后、Blink 前购买 Shard**；不为此杜撰另一件最佳装备，按既有合法出装顺序继续。用户自定义出装不因这个默认选择被禁止；特殊模式或通过游戏机制获得免费的 Shard 单列观察，不宣称能够有效利用。
- 这是一条**OHA-Next 工程策略**，并非断言高水平玩家不应该购买 7.42 的 Shard；人类/高水平玩家可能有效使用新拾取与投掷。
- 恢复默认购买的最低要求：核验技能名字和实际动作结果；设定具有战斗价值的施放与拒绝场景；比较携带者缴械、兵线/单位价值、投掷机会与更好技能的成本；对关键反例完成离线测试，标记 VT-001～VT-004、VT-014 的客户端验证状态；之后再决定优先级。

实现记录：默认出装调整分别写入 [PR #4](https://github.com/littleredcap/dota2bot-OpenHyperAI/pull/4) 及堆叠实验 [PR #5](https://github.com/littleredcap/dota2bot-OpenHyperAI/pull/5)，仍是待审查代码，**尚未合并或游戏验证**。

## 5. 策略条目应如何记录

新增策略时用一个稳定的条目（可以在本目录后续单独建 `STRAT-xxx` 记录）：

```text
strategy_id:
phase: 选人/对线/拉野/刷野/抓人/团战/地图目标/上高/守高
scope: 通用 / 角色 / 英雄 / 阵容 / 对手
objective: 怎样提高最终胜率（可证伪假设）
official_patch_mechanic:
community_sources_and_dates:
preconditions_and_legal_observations:
preferred_action:
alternatives_and_when_not_to_do_it:
opportunity_cost_and_regret_case:
hero_role_variations:
existing_code_coverage:
guide_maturity: R0/R1/R2/R3
implementation: I0/I1/I2/I3
strength_evidence: W0/W1/W2
patch_status: current/needs_patch_review/outdated
client_validation_ids:
pr_ids:
status: idea/research/experimental/accepted/deferred/rejected
```

**持续发现机制的触发：** 开发 F 类能力、发布新补丁、用户提出异常或主动请求研究时，检查官方补丁、当版本高分/职业复盘、战术攻略、社区讨论和其它 Bot 实现；提取有反例的 STRAT/IDEA 候选，按潜在胜率贡献×可信度×可实现性排序，给出为何做/为何不做。此流程只是一种约定，**未创建后台持续监测任务**。

## 6. 当下第一批建议审查的策略

- **通用兵线、资源分配与支援条件**：对线/拉野/刷野怎样在收益与保护核心之间平衡；先核查现有 `mode_laning_generic.lua`、`mode_farm_generic.lua` 与游走逻辑，不预设它们有 Bug。
- **团战和打赢之后的资源转换**：击杀以后是否有条件推塔、控图或打盾；不只优化击杀率。
- **Roshan 争夺与放弃**：F-10，判断是确证、怀疑、侦察、集结、偷盾、换线还是守家；先确认现有实现范围。
- **Meepo 魔晶**：属于 R1 新版实验；保持默认不购买且 AI 功能关闭，等待可信的客户端与收益证据。
- **7.42 新物品、地形与魔方目标**：优先检查 API、地图有效性，避免旧机制错误；再讨论最优打法。

**验收边界：** 当前先形成可复用策略研究目录，非一次性编写十种复杂系统。成熟攻略优先只是研发起点；最终仍以有证据的公平胜率和鲁棒性为准。
