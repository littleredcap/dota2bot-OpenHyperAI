中塔的问题至少有三段：**守塔人离开/没人接班 → 可处理的攻城车没打掉 → 两核心在敌塔侧先死**。前一次改动依赖即时威胁出现后派人，从这场看不足以防止空中。静态审查确认下面是候选，不是录像已经证明命中的分支：

1. `GetOuterTowerThreat` 区分攻击塔、已目击英雄和护送波，但“中路组团”仍依赖至少三名向塔移动/攻击的可见英雄及两只兵。单攻城车已有单独判断，不应再把它当团战；实战中需要核实威胁是否早已识别，但没人可达、无安全站位、被更高优先级动作覆盖，还是检测本身没看到。
2. `GetEarlyMidSiegeDefense` 只在 4–16 分钟、且中单距己方中 T1 不超过 2,200 时介入；`GetDefendDesireHelper` 在没有分到明确守塔任务时还可能被己方推进意图压低。这两条都没有提供“中单离开后替补接当值”的保证。下一轮应测试交接与跨目标仲裁，非把半径再加一圈。
3. Glyph outer 防守决策依赖能在窗口内兑现的清线员等条件；前面两层未花时应记录按不住的具体原因，排除 API 冷却门槛、没有守将、保护收益条件这几类，不应改成见掉血就盲开。
4. 用真实可见输入记录中塔波次、威胁分类、候选者/ETA/TP 冷却与安全落点、选中模式、首条实际命令和动作结果。相邻事件节流；不可读取敌方战争迷雾。录像全知的位置只用于事后比对，不能直接当脚本先验。
