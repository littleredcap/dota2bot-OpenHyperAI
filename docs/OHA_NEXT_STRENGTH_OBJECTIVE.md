# OHA-Next：公平竞技强度目标与评估准则

> **已确认产品目标 A**：2026-11-19 用户明确选择“尽可能强的 AI，以公平条件下的实战获胜能力为核心”。  
> 本文是产品目标和未来验收规范，不表示已测试出胜率提升。  
> 关联：[需求清单](OHA_NEXT_REQUIREMENTS.md) · [目标架构](OHA_NEXT_ARCHITECTURE.md) · [协作规范](UPSTREAM_AND_FORK_WORKFLOW.md)  
> 当前实施边界：**先做玩法需求与小范围改动**；故障监控、自动批量对局与数据自动回传保持 deferred。

## 1. 什么叫“强”

**正式定义：** 在相同且合法的 Dota 2 游戏规则下，不给 OHA-Next 额外资源、属性或不可合法得知的信息，让它依靠自己的策略、操作、团队合作与适应能力，在有代表性的对手、阵容、阵营与局势分布中，获得更高的**实战获胜概率**。

这是**结果导向的目标**，不是让机器人看起来像高手。可使用不太像人类但符合游戏与 Bot API 规则的有效打法，不人为限制反应速度或 APM 来模拟人类；仍须尊重游戏内施法前摇、冷却、行动和可见信息等规则。

**不把“更难打”等同于“更强”：** 人为增加金币、经验、属性、装备、复活优势或提供敌方迷雾内的真实位置，只改变了比赛条件，不能作为本项目默认强度提升的依据。

**也不限制 Bot 正常赚到更多资源：** 补刀更好、有效打野、少死、赢团、拆塔和控图，带来更高 GPM/XPM 是合法的**策略成果**，不是作弊；我们反对的是*额外发放*而非*赢得更多*。

## 2. 公平竞技边界（强度比较的入场条件）

| 类别 | 允许 | 不允许 / 必须隔离 |
| --- | --- | --- |
| 经济和经验 | 与对手遵循同样的地图、击杀、补刀和经验规则，靠策略形成优势 | FretBots、Buff 或自定义脚本向 OHA-Next 单独注入额外金币、经验、属性、专属装备、特殊回复/复活优势 |
| 视野与信息 | 使用自身/队伍依法可见的信息、战争迷雾下的最后已见位置及其时间戳、合理概率推断 | 利用测试观察者或引擎隐藏状态直接知道当前不可见敌人位置、敌方资源和私人状态；分析端真值不得回流策略 |
| 操作 | 使用官方允许的 Bot Scripting API 执行合法连续命令、反应和组合技能；不强求模仿人类手速 | 绕过技能/物品冷却、资源消耗、施法规则、碰撞或游戏权限；伪造动作成功 |
| 条件一致性 | 正常对局条件下对比，同版本、同模式、相同规则，匹配阵容并交换阵营 | 拿本项目的加成模式对别人的正常模式，或者用不同游戏版本/地图条件硬比较强度 |
| 学习和适应 | 根据合法局内观察动态调整；使用合规的历史公开统计学习一般策略 | 把尚未发生的局内事件、测试集隐藏答案或仅属于对手/裁判的私密真值喂给实战 AI |

**增强难度单列：** FretBots/ Buff 的加成可以继续作为娱乐玩法或非公平压力测试，但要明确标注模式；无论胜率多高，都不能混入“公平模式强度”数据。

## 3. 目标函数与指标优先级

从优化角度，把在**预先定义的公平对手与局势集合**中获胜视作最终目标。对局数据完整且版本、配置可信时，主要比较候选版本相对基线的有效完赛胜率与对手强度。此处暂不预设“必须提升 5%”等无依据的门槛。

| 层级 | 指标与作用 | 决策纪律 |
| --- | --- | --- |
| **约束层（必须满足）** | 公平性、功能兼容、合法信息与行动、可核验的版本身份 | 不满足即不能称公平强度进步 |
| **首要结果** | 对明确对手的获胜概率/有效完赛胜率，并报告样本量、侧别与不确定性 | 最重要，但少量对局或单一对手胜率不足以证明全面更强 |
| **泛化与鲁棒性** | 面对不同对手、英雄阵容、优势/劣势、天辉/夜魇的表现，是否存在严重退化 | 不追求只针对固定弱 Bot、固定阵容的胜率刷分 |
| **诊断与中间产出** | 合法补刀/GPM/XPM、击杀与死亡、有效技能使用、推进与控图、目标转化、团战、无效行动 | 用于解释强弱和定位问题；不直接代替输赢 |

**指标冲突时的原则：**
- GPM 上升、胜率下降：不能算成功的强度提升；可能过度刷钱、错失推进或团战。
- 死亡下降、胜率下降：可能过度保守，不能因为 KDA 更漂亮就宣称更强。
- 技能命中率上升，但输出、控场或赢团下降：不能仅凭命中率断定更强。
- 推塔更快但频繁团灭：需要比较稳定的获胜效果，而非只看最快局。
- 兼容 7.42、修好空对象调用：属于**正确性与基础保障**；重要且可优先处理，但本身不等于已证明胜率提高。

## 4. 有助于赢比赛的能力维度（研发假设，不是既定 Bug）

| 维度 | 实际能力目标 | 不可只看的指标 | 当前需求对应 |
| --- | --- | --- | --- |
| 对线与发育 | 在安全和对线压力之间权衡补刀、反补、换血、支援，减少无收益发育 | GPM、补刀数 | F-04 |
| 团战与微操 | 优先正确目标、技能与物品时机、队友救援、合法连招、追击/撤退 | 击杀数、命中率 | F-02、F-05 |
| 地图与目标 | 将兵线和团战优势兑换成建筑、Roshan/Tormentor、经济资源和最终胜利 | 单一推塔数、Roshan 次数 | F-06、F-07 |
| 资源配置与阵容适应 | 根据可见信息、英雄角色、双方阵容调整装备、路线和策略 | 单件装备伤害、净资产 | F-08 |
| 可靠性与版本适配 | 避免因过期技能、无效物品、无效动作或规则冲突让整场决策失效 | Lua 语法检查“通过” | F-01、F-03 |
| 泛化与覆盖 | 不依赖单一英雄、对手、阵营、游戏模式或局势套路才能赢 | 一套阵容胜率 | F-09、D-07 |

**策略目标会随游戏改变。** 落后时可以交换资源、拖时间并寻找翻盘机会；领先时应考虑控图、压制、争夺目标和结束比赛；是否打架、让线、支援或拆塔，取决于它们对**未来获胜可能性**的影响，而不是固定事件次数。

目前不把强化学习模型、远程 LLM 推理或整库架构重写列为必须选用的方案。是否引入某种算法，要看其成本、可靠性和对实战胜率的净贡献；规则系统、评分、状态机和外部训练皆可作为**待验证手段**。

## 5. 公平强度评估协议（未来实施，当前不启用批跑系统）

### 5.1 先对照，后宣称更强

强度实验要明确定义：`baseline_sha`、`candidate_sha`、Dota 构建/补丁、模式、英雄及角色、阵营映射、对手版本、是否存在额外奖励、胜负及其可信来源。

- **至少两类对手基线**：同项目上一版 / 原作者基线是持续回归参考；另从经过许可和兼容检查的不同风格对手中选代表。Valve 默认 Bot 可作低门槛冒烟基线，不能成为唯一强度证明。具体对手池尚未决定。
- **匹配和换边**：尽量用相同阵容与条件做换边或配对比较，检查天辉/夜魇优势；随机种子仅在当前环境证实可控时使用。
- **同版本隔离**：比较不同 Bot 版本时必须确认双方加载了正确源码与配置；未验证 VM / require 缓存隔离时，不假定同场 A/B 成立。
- **防止针对测试集过拟合**：研发场景与最终验收场景分开，换阵容、换对手与局势；对一类局面特化后要检查其它常见局面是否退步。
- **诚实统计**：报告全部运行尝试、完成数、排除原因、有效完赛数与胜率分母；给出区间估计/不确定性并遵循事先确定的样本计划和停止条件。小样本的正向变化通常只能叫“初步信号”，不能叫“已证实变强”。
- **对局加速与增强模式**：加速必须先确认不显著改变关键决策机制，正常倍率和加速数据分别标记；FretBots/ Buff 资源加成测试永不与公平测试混算。

### 5.2 可使用的结论等级

| 状态 | 何时可以用 | 不能怎么说 |
| --- | --- | --- |
| `compatibility_identified` | 有版本补丁 + 当前源码的静态不匹配 | 不能说“游戏内已重现” |
| `logic_checked` | 静态检查与针对性的离线断言通过 | 不能说“胜率已提高” |
| `game_checked` | 在真实游戏构建观察到相关场景功能正常/修复 | 不能自动推广到所有英雄和局势 |
| `strength_signal` | 有公平对照的完整数据，结果方向为正但不确定性较大 | 不能称“确定比上版本更强” |
| `strength_supported` | 充分的公平对照、对手/阵容覆盖与不确定性评估支持改进，未发现不可接受的关键退化 | 仍需注明限定对手池、版本和测试条件 |
| `regression` / `inconclusive` | 出现退步或数据不足/冲突 | 不能默认为成功；需复查或撤回结论 |

这个强度结论体系与需求文件的 **E0–E4 缺陷证据等级不同**：E 等级回答“Bug 是否有依据”，上表回答“修复/优化是否使 AI 更强”。

### 5.3 现状限制

**截至 2026-11-19：** PR #1 只有局部 Lua 离线用例；PR #3 是 7.42 静态审计。没有已校准、可反复运行的公平对局评估平台，也没有可用的正式胜率提升数据。用户已明确要求暂停监控/批跑建设，**不能为实现本文评估协议而先行搭建该设施**。功能开发可先通过源码审查、可复现局部测试和人工 PR 审核推进，所有“实战更强”结论保留待验证状态。

### 5.4 从成熟玩法到全局打法的可追溯路线

研发应该覆盖**从选人、对线到上高结束比赛**的全部决策环节，区分通用、英雄/角色专属和全队策略。先核验 OHA 已有实现，再优先学习当版本机制可靠、具有明确适用条件与反例的攻略，避免为了覆盖技能而让 Bot 无条件释放。具体策略矩阵、R（攻略成熟度）/I（实现状态）/W（公平强度证据）分别见 [整局策略图谱](GAMEPLAY_STRATEGY_CATALOG.md)。

**装备选择必须与行为能力相符。** 若某件装备主要提供的新主动暂时没有可靠策略，既未验证 Bot API，也不能说明收益超过其金币和时机成本，就不应被放进默认核心早购顺序；但被动价值明确的物品、可作为反制物品的购买应单独判断。7.42 Meepo 魔晶目前属于暂缓默认早购的实验项，**不能因此推出真人高水平玩家不应该购买此装备**。

当前的成熟策略优先是**研发排序原则**，不是“未经实战就证明最佳”；新机制可保留研究原型，等有证据再启用。

## 6. 需求筛选与 PR 决策

不要按 Stars、Fork 提交数、代码长度、英雄技能数量、GPM 或“看起来很聪明”排优先级。建议依次判断：

1. **入场条件**：是否影响正常公平游戏的兼容和安全？明确的核心版本问题优先于纯外观改动。
2. **获胜链路**：该问题如何使我们失去/获得胜利？例如重大团战失误、Roshan 判断、补刀牺牲推进；列出可被证伪的假设。
3. **实际证据**：区分 E0 构想、E1 外部报告、E2 本分支源码风险、E3 离线复现、E4 游戏复现；优先审查**影响大且证据充分**的条目。
4. **投入与退化风险**：改动范围、受影响英雄/场景、回滚能力、破坏其它策略的可能性。
5. **验收**：局部代码测试证明正确性；真正的强度收益以后靠合法的公平对照确认。没有对照时，标注“胜率收益尚未证明”。

每一个能力优化 PR 应填写：

```text
需求 ID：
原始现象 / 证据等级与来源：
可证伪假设：如果修复/调整 X，将降低 Y 的失误，从而改善 Z 类取胜机会
影响英雄/角色/模式：
公平性影响（额外资源/属性/信息/特殊操作）：无 / 已说明
变更与兼容性：
局部验收（T0/T1）：
真实对局/强度对照：未执行 / 已执行（附版本与证据）
已知退化与回滚：
对强度的结论：待验证 / 有初步信号 / 有充分支持 / 发现回归
```

## 7. 明确非目标

- **不以像真人、聊天、故意降低 APM 或模拟人类失误作为优化约束。**
- 不通过 FretBots/ Buff 的额外经济、经验、属性、非法信息或额外装备提高公平排行榜表现。
- 不把更短比赛、更高 GPM、更多击杀、更低死亡等代理指标优化成唯一目标。
- 不为赢固定简单对手而牺牲普遍的竞技表现，也不把不适用的旧补丁数据当新版本事实。
- 不承诺固定胜率提升、绝对最强、在所有英雄/模式中都更强；强度结论必须限定条件与证据。

**目标确认状态：** A 已由用户明确选择；文中的对手池、首个游戏模式、胜率检验门槛、评估预算和方法实现属于后续工程建议/待定项，并非已经选择或部署。
